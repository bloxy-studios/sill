# Alpha-Omega (OpenSSF)

Status: CURRENT — but no open application process (Last verified: 2026-08-21)

## Program

An OpenSSF-associated project funded by Microsoft, Google and AWS whose mission is to "catalyze sustainable security improvements to critical open source projects and ecosystems." Operates in two halves: Alpha, deep direct engagements with a small number of the most critical projects and foundations; Omega, automated vulnerability discovery across large numbers of projects. Active since 2022.

## Official URL

https://alpha-omega.dev/ (project repo: https://github.com/ossf/alpha-omega)

## What it funds

Security capacity at the top of the dependency graph: funding dedicated security staff inside foundations (Rust Foundation, Eclipse Foundation, Python Software Foundation), security improvements in projects like Homebrew and Node.js, security audits of projects like OpenSSL, security features in projects like Rustls, and bulk vulnerability identification work.

## Eligibility

No published open-call eligibility criteria and no application form. Named Alpha engagements are with foundations and top-tier ecosystem projects: Eclipse Foundation, FreeBSD Foundation, Homebrew, Node.js, OpenSSL, OpenRefactory, Prossimo, Python Software Foundation, Rust Foundation. The de facto bar is being a project or foundation whose compromise would affect a large fraction of the software supply chain. Contact is via a membership/engagement inquiry form rather than an application.

## Typical funding

UNKNOWN per engagement. Engagements are multi-year staffing arrangements with foundations rather than project grants; no per-project figures are published on the pages reviewed.

## Application requirements

No application. Interested parties can join the OpenSSF #alpha_omega Slack channel, the alpha-omega-announcements mailing list, or the monthly meeting (first Wednesday, 9:00 PT), and contact the team via alpha-omega.dev.

## Sill fit

NOT ELIGIBLE, and unlikely to ever be. Alpha-Omega funds the load-bearing base of the software supply chain — language runtimes, package managers, TLS libraries, OS foundations. A desktop terminal application is not in that category regardless of how successful it becomes. This is a structural mismatch, not a maturity gap.

## Missing evidence

- Not applicable. No plausible path exists for a desktop application.
- The only theoretical route: a security-critical library extracted from Sill that becomes a widely-depended-upon component, which is a different project.

## Application strategy

Do not pursue. For security-flavoured funding, use the GitHub Secure Open Source Fund instead — same broad goal, dramatically lower bar, and designed for exactly the individual-maintainer case that Alpha-Omega is not. Record this as checked and closed.

## Deadline

None — no application cycle exists.
